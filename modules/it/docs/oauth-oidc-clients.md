# OAuth / OIDC Clients

The Staff Portal backend now exposes Laravel Passport endpoints for third-party OAuth2 clients while keeping the existing Staff Portal SPA on Sanctum and the legacy cross-app SSO JWT flow in place.

## Backend base path

Use the backend app URL, including the real path prefix for this deployment:

- Local/default: `http://localhost/staff/staff-portal/backend`
- Production: `<APP_URL>/staff/staff-portal/backend` when the app is deployed under the shared `/staff` prefix

All URLs below are shown relative to that backend base.

## OAuth endpoints

Core Passport endpoints:

- Authorize: `GET /staff/staff-portal/backend/oauth/authorize`
- Token: `POST /staff/staff-portal/backend/oauth/token`
- Token refresh: `POST /staff/staff-portal/backend/oauth/token/refresh`
- User info for Passport bearer tokens: `GET /staff/staff-portal/backend/api/v1/oauth/user`
- OpenID discovery: `GET /staff/staff-portal/backend/.well-known/openid-configuration`
- OAuth-prefixed discovery: `GET /staff/staff-portal/backend/oauth/.well-known/openid-configuration`
- JWKS: `GET /staff/staff-portal/backend/oauth/jwks`

Local examples:

- `http://localhost/staff/staff-portal/backend/oauth/authorize`
- `http://localhost/staff/staff-portal/backend/oauth/token`
- `http://localhost/staff/staff-portal/backend/oauth/token/refresh`
- `http://localhost/staff/staff-portal/backend/api/v1/oauth/user`
- `http://localhost/staff/staff-portal/backend/.well-known/openid-configuration`
- `http://localhost/staff/staff-portal/backend/oauth/.well-known/openid-configuration`
- `http://localhost/staff/staff-portal/backend/oauth/jwks`

## OIDC discovery and JWKS

Laravel Passport 13 in this app provides the OAuth2 authorize/token endpoints, but it does not publish OpenID Connect discovery metadata or a JWKS document on its own here. The backend therefore exposes a minimal companion discovery document and JWKS endpoint so other internal apps can auto-configure against the real Passport endpoints.

Discovery document fields:

- `issuer`: backend base URL
- `authorization_endpoint`: Passport `/oauth/authorize`
- `token_endpoint`: Passport `/oauth/token`
- `userinfo_endpoint`: `GET /api/v1/oauth/user`
- `jwks_uri`: `GET /oauth/jwks`

This is intended for endpoint discovery and signing-key publication. Token issuance still follows Passport OAuth2 flows already documented above.

## Current auth split

These auth paths now coexist:

- Staff Portal SPA: Sanctum bearer tokens on existing SPA API routes such as `GET /staff/staff-portal/backend/api/v1/me`
- Legacy CBP app SSO: existing JWT-based endpoints such as `POST /staff/staff-portal/backend/api/v1/sso/validate` and `GET /staff/staff-portal/backend/sso/callback`
- New OAuth clients: Passport on `/staff/staff-portal/backend/oauth/*` plus `GET /staff/staff-portal/backend/api/v1/oauth/user`

Do not remove or repoint the legacy SSO JWT consumers until each app is fully migrated.

## PKCE example for public clients

Browser and mobile apps should use Authorization Code + PKCE with a public Passport client.

### 1. Redirect the signed-in user

Example authorize URL:

```text
http://localhost/staff/staff-portal/backend/oauth/authorize
  ?client_id=YOUR_PUBLIC_CLIENT_ID
  &redirect_uri=https%3A%2F%2Fapp.example.test%2Foauth%2Fcallback
  &response_type=code
  &scope=
  &state=RANDOM_CSRF_STATE
  &code_challenge=BASE64URL_SHA256_VERIFIER
  &code_challenge_method=S256
```

Parameters to send:

- `client_id`: Passport client ID shown in the OAuth Clients admin UI
- `redirect_uri`: one registered redirect URI for that client
- `response_type=code`
- `scope`: optional, empty string is acceptable for the current internal usage
- `state`: CSRF correlation value generated by the client app
- `code_challenge`: base64url-encoded SHA-256 hash of the verifier
- `code_challenge_method=S256`

### 2. Exchange the authorization code

Submit a `POST` to `http://localhost/staff/staff-portal/backend/oauth/token`:

```json
{
  "grant_type": "authorization_code",
  "client_id": "YOUR_PUBLIC_CLIENT_ID",
  "redirect_uri": "https://app.example.test/oauth/callback",
  "code": "AUTHORIZATION_CODE",
  "code_verifier": "ORIGINAL_RANDOM_VERIFIER"
}
```

Confidential clients should include their `client_secret` in the token request. Public clients must not send one.

### 3. Call the user endpoint

Use the returned access token against:

```http
GET /staff/staff-portal/backend/api/v1/oauth/user
Authorization: Bearer <access-token>
Accept: application/json
```

## Legacy SSO JWT coexistence

The OAuth rollout does not replace the existing JWT-based SSO immediately.

- Existing module launch / callback flows can continue using the current JWT flow.
- `POST /api/v1/sso/validate` remains the validation endpoint for legacy consumers.
- Passport should be used for new integrations and for staged migrations of older apps.

## Migration checklist for APM / Helpdesk

Use this checklist when moving a legacy JWT consumer to Passport:

1. Register a dedicated Passport client in the OAuth Clients admin screen and capture the generated client ID.
2. Choose the client type:
   - public + PKCE for browser/mobile SPAs
   - confidential for server-side web apps that can safely store a secret
3. Add the new redirect URI(s) for the app under `/staff/staff-portal/backend`.
4. Replace legacy JWT launch/validation calls with the Passport authorize + token exchange flow.
5. Use `GET /staff/staff-portal/backend/api/v1/oauth/user` as the first authenticated identity check after token issuance.
6. Keep the old SSO JWT integration live during parallel rollout until sign-in, callback handling, and user bootstrap are validated in production.
7. Remove shared-secret JWT assumptions only after the Passport path is fully cut over for that app.

## Notes

- The OAuth client admin UI reveals a confidential client secret only once, immediately after creation.
- Public clients do not receive a secret, but they still receive a stable client ID that should be recorded at registration time.
